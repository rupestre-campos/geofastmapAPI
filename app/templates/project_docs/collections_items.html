Collections & items (features)

A collection is a dataset (layer). Each collection has items (features) with geometry and properties.

Storage model

  • Features live in Postgres and are partitioned by collection_id for performance.
  • Collections keep a cached feature_count for fast listing.
  • Geometry is stored as PostGIS geometry; properties are stored as JSON.

Importing data

  • Bulk import runs asynchronously (job-based).
  • Optionally you can queue a static tile build after import completes.
  • Import modes typically include append (add features) and replace (delete then import).

Visibility & sharing

  • private: only owner (and explicit shares) can see.
  • logged: any authenticated user can see.
  • public: anyone can see (including anonymous).
  • Editor shares grant edit access without changing visibility.

Search & filtering

  • Item listing supports bbox, structured filters, and (in some contexts) full-text search across properties.
  • Short full-text queries can be expensive; minimum lengths may be enforced to protect performance.
  • When performance matters, prefer filters on indexed properties and bounding boxes.

Operational tips

  • Use static tiles for “browse” and public maps; use dynamic tiles for ad-hoc filtering workflows.
  • After large imports, rebuild static tiles and recompute extents to keep UI fast and accurate.
  • Keep property payloads lean (especially on tiles); huge properties degrade both DB and client performance.
