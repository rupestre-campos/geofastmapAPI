Collections & items (features)

A collection is a dataset (layer). Each collection has items (features) with geometry and properties. To use this API in QGIS or ArcGIS Pro as OGC API Features, see QGIS & ArcGIS (OGC API).

Storage model

  • Features live in Postgres, LIST-partitioned by collection_id. Each collection gets a dedicated partition when created (or on the next bulk import). Rows that predate partitioning may sit in features_default until migrated.
  • Full replace uses TRUNCATE on the collection partition (fast). replace_filtered uses batched DELETE with your filter lines.
  • Collections keep a cached feature_count for fast listing.
  • Geometry is stored as PostGIS geometry; properties are stored as JSON.

Importing data

  • Bulk import runs asynchronously (job-based).
  • Optionally you can queue a static tile build after import completes.
  • Import modes: append (add features), replace (delete entire collection then import), and replace_filtered (delete only features matching property filters, then import). Filtered replace uses the same key:op:value lines as item search (e.g. state_id:eq:12, date:lt:2026-07-12); multiple lines are combined with AND.

Large files, Cloudflare (~100 MB), and chunked browser uploads

Bulk import is exposed as one HTTP POST per file: the browser sends the entire upload in a single request, and the API streams it to disk (then the worker reads that complete file with Fiona/GDAL, including zip/shapefile and GPKG).

Splitting a file in JavaScript only in the browser does not bypass Cloudflare’s per-request size limit unless the server exposes a separate protocol to accept many small requests and reassemble them into one file before import. GeoFastMap does not ship that today—so for public hostnames behind Cloudflare, treat ~100 MB (typical Free/Pro cap) as a hard ceiling for browser uploads.

Practical options today (no new API):

  • Import from localhost or LAN IP to the machine running the API (no Cloudflare edge in the path).
  • Split the dataset into several files under the limit and use Append for each import.
  • Use a VPN or other private path that does not send the upload through Cloudflare.
  • A later CLI or desktop tool can talk directly to the origin the same way.

If chunked uploads are added in the future: a server-side session (upload id, chunk index or byte offset) would append chunks to a temp file until complete, then enqueue the existing bulk job on that path. In the browser, using Blob.slice() and uploading chunks sequentially (or with low concurrency) keeps RAM low by not loading the whole file into memory at once—each chunk is only a small slice. That would be new API surface, not a change to the core importer logic.

Visibility & sharing

  • private: only owner (and explicit shares) can see.
  • logged: any authenticated user can see.
  • public: anyone can see (including anonymous).
  • Editor shares grant edit access without changing visibility.

Search & filtering

  • Item listing supports bbox, structured filters, and (in some contexts) full-text search across properties.
  • Short full-text queries can be expensive; minimum lengths may be enforced to protect performance.
  • When performance matters, prefer filters on indexed properties and bounding boxes.

Operational tips

  • Use static tiles for “browse” and public maps; use dynamic tiles for ad-hoc filtering workflows.
  • After large imports, rebuild static tiles and recompute extents to keep UI fast and accurate.
  • Keep property payloads lean (especially on tiles); huge properties degrade both DB and client performance.
