Advanced setup: distributed on owned hardware

Work in progress. This page mirrors the lab guide in the repo. The supported default for everyone is still single-machine docker compose up—see Deployment & performance and the README / docs/DEPLOYMENT.md in the repository.

Mission

Run GeoFast across machines you already own, with no cloud hosting bill for the app stack (local disks, LAN). A Raspberry Pi may run Cloudflare Tunnel only as the HTTPS edge—do not run the full Docker stack on the Pi if it hosts other critical services.

Hardware this guide is written for

Machine Specs Role (why)
Primary machine e.g. 8 cores, 16 GB RAM, NVMe Main server: PostgreSQL, Redis, API, workers, Titiler, all data volumes. In an optional second phase, also NFS/SMB exports so worker hosts share /data/... paths.
Small worker machine(s) e.g. 2c/4t, 8 GB, HDD (optional) Optional extra workers only—run deploy/compose/docker-compose.workers.yml with DB/Redis on the primary. Use for more process_worker throughput; heavy Tippecanoe on weak disks/RAM is still a poor fit unless storage is shared and fast enough.
Raspberry Pi — Edge only: cloudflared tunnel → one LAN origin (usually the primary API port). Not for Postgres/Redis/Tippecanoe.

Phase 1 — default (recommended first)

Run the entire stack on the primary machine with the root docker-compose.yml (docker compose up). Point the Cloudflare tunnel private origin to http://<PRIMARY_LAN_IP>:8000. No second host or NFS required.

Primary checklist (summary)

  • Install Docker + Docker Compose.
  • Clone the repo, set production secrets (AUTH_SECRET_KEY, TITILER_INTERNAL_SECRET, DB passwords).
  • docker compose up -d --build; verify http://<PRIMARY_IP>:8000 on the LAN.
  • Firewall: expose the API port to LAN + Pi only, not the open internet (except via Cloudflare).

Pi checklist (tunnel only)

  • Install cloudflared; configure tunnel origin to the primary API URL.
  • Do not run GeoFast Docker containers on the Pi for this setup.

Phase 2 — optional small worker machine + primary as file server

Keep Postgres, Redis, API, Titiler, and all file data on the primary. Export /data/tiles, /data/bulk-uploads (as needed) via NFS or SMB; mount those paths identically on the worker host before starting workers. On the small machine, run only workers from deploy/compose/docker-compose.workers.yml with DATABASE_URL and REDIS_URL pointing at the primary. A common first step is process_worker only (more layer / intersection throughput) without exporting rasters.

NFS (recommended): run nfs-kernel-server on the primary host (outside Docker). Step-by-step commands, /etc/exports, firewall, and worker mounts are in the repository at docs/lab/nfs-host-ubuntu.md. An optional Docker-based helper (deploy/compose/docker-compose.nfs.yml) exists for experiments; see deploy/compose/README.md for caveats.

Raster / COG: conversion runs synchronously in the API on upload today—keep rasters on the primary unless you add async jobs later.

Multiple process_worker instances usually scale; share one canonical deploy/env/.env.workers (secure-copy from the primary). Avoid accidental duplicate full stacks; prefer workers-only compose on the second host.

What must match when you split hosts

  • One logical DATABASE_URL, one REDIS_URL for all workers talking to the primary.
  • Same BULK_STORAGE_PATH / TILES_STORAGE_PATH on disk wherever those services read or write—typically NFS from the primary with identical mount paths.
  • Same AUTH_SECRET_KEY on every API instance; same TITILER_INTERNAL_SECRET for Titiler internal fetch.
